# GameClawEngine AI 原生开发原则

> 本文档定义 GameClawEngine 所有技术决策所依据的基本原则。这些不是建议，而是铁律。每一行代码、每一个数据结构、每一次架构选择，都必须能对照这些原则说明理由。

## 铁律 1：AI 是第一开发者，人类是验收者

所有数据格式、API 接口和错误信息的设计，都必须围绕一个核心问题：**「AI 生成和消费这些数据的成本与准确性如何？」**

- 人类可读性是加分项，不是设计约束。
- 当「对 AI 友好」与「对人类友好」冲突时，以对 AI 友好为准。
- 引擎是为 AI 而建，而不是为「把 AI 当副驾的人类开发者」而建。

## 铁律 2：Token = 成本，字节 = 货币

在生成式 AI 应用中，Token 推理成本是初创团队的头号杀手。

- 以 **TOON 格式**（而非 JSON）作为与 AI 通信的主数据格式。
- TOON 相比 JSON 可节省约 30–60% 的 token；在百万级用户规模下，这直接决定盈利与破产。
- 所有数据结构设计都必须考虑 token 效率：
  - 扁平结构优于深层嵌套
  - 短键名优于长描述名
  - 枚举约束优于自由文本
- 禁止：冗余字段、注释字段、仅「给人看」的装饰性数据。

## 铁律 3：数据与逻辑必须彻底分离

- Game IR（TOON 格式）是**唯一事实源**。
- Godot 运行时仅是 IR 的「投影幕布」——负责渲染与物理碰撞，**绝不**做逻辑决策。
- AI 从不直接生成或修改 GDScript/C++ 代码，只输出符合规范的 IR 数据。
- 所有游戏状态变更必须通过 Patch 事务完成；禁止直接改 Godot 节点属性。

## 铁律 4：事务性与回滚是生命线

- 每一次 AI 修改都是一次**原子事务**。
- 事务必须包含前置条件测试（`test` 操作），防止并发导致状态污染。
- 任何异常都会触发自动回滚——AI 幻觉**绝不能**污染游戏状态。
- 系统维护完整的 Patch 历史，支持回溯到任意历史状态。

## 铁律 5：序列化格式必须可插拔

- 虽然 MVP 使用 TOON，但所有 IR 读写都必须经过抽象的 **Codec 接口**。
- Codec 接口约定：
  - `encode(data: Dictionary) -> String`
  - `decode(text: String) -> Dictionary`
- 引擎内部以 Godot `Dictionary` 为中间表示，与序列化格式完全解耦。
- 未来可无缝切换其他格式（二进制 TOON、自定义 DSL、直接 token-id 编码），而无需动核心逻辑。

## 铁律 6：分层模型路由，拒绝单一依赖

- AI 编排层必须支持多模型路由（Provider Router）。
- 简单任务用便宜小模型，复杂推理用大模型。
- BYOK（自带 Key）为默认模式——平台不承担推理成本。
- 所有 AI 调用必须有超时、重试与降级策略。

## 铁律 7：安全边界不可突破

- AI 输出的 IR 在进入引擎前必须通过 Schema 校验。
- 禁止 AI 直接访问文件系统、网络或进程资源。
- 内容安全预审（文本 + 图像）是强制项，不是可选项。
- 所有 AI 生成内容必须可追溯：谁生成、用哪个模型、用哪条 prompt。

## 铁律 8：分层假设，证据驱动

任何「行为与预期不符」在排查前都必须先拆成层次。

- **GameClawEngine 层次模型：** IR 输入 → Patch 事务 → IR 状态 → 投影（SceneTree）→ 渲染输出。
- 从渲染/输出层向输入层反向追溯。
- 每个假设都必须有源码或运行时数据支撑，禁止猜测。
- 在提出修复前，先确认：根因在哪一层？有什么运行时证据？

| 层次       | 典型现象               | 观测方式                         |
|------------|------------------------|----------------------------------|
| IR 输入    | TOON 解码失败、Schema 违规 | `validate_ir`、`decode_toon`     |
| Patch 事务 | 前置条件失败、路径不存在   | `apply_patch` 错误详情、`get_patch_history` |
| IR 状态    | 值异常、实体缺失         | `get_ir_state`、`query_ir_path`  |
| 投影       | 节点未创建、属性未同步    | `inspect_scene_tree`、`get_entity_node_props` |
| 渲染输出   | 画面错但数据对          | `capture_screenshot`、`capture_viewport` |

## 铁律 9：先观察再修改

再多的推理也抵不过一条运行时证据。

- **排查链：** 静态分析（读配置/代码）→ 形成假设 → 运行时观察 → 验证或推翻。
- 每个验证周期只做一处修改，不要一次改多处再一起验证。
- 观察优先级（成本从低到高）：
  1. 读已有日志（`read_godot_log`）
  2. 单次状态查询（`get_ir_state`、`inspect_scene_tree`）
  3. 帧级持续打点（`start_frame_probe` / `read_probe_log`）
  4. 受限运行时求值（`eval_gdscript`）
  5. 改源码（最后手段）

## 铁律 10：单变量隔离

在调试或调参时，一次只改一个变量，然后立刻验证。

- 同时改多个变量无法归因。
- 每次验证前确认：
  - 配置确实已重新加载（不是旧缓存）。
  - 观测脚本确实在跑（不是上次的残留日志）。
  - 复现步骤与上次完全一致（受控实验）。
- **反模式**（严格禁止）：
  - 在无运行时证据的情况下连续做多处修改。
  - 不读实现就假设 API 行为。
  - 假设某参数「没被改」而不核对所有写点。
  - 改多个文件后只做一次验证。
